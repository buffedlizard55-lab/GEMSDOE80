Exact steps to make a submission (no manual inspection needed)

  1. Get the data (login required once). Log in at DrivenData competition #306 data page and download into data/: training_features.tif, labels.tif, sample_submission.tif, 1m_DEM_links.csv. Keep data/ out of Git (.gitignore already excludes it).
  2. Confirm placement. python scripts/prepare_data.py — prints the official grid report (CRS, shape, transform, dtype, bounds).
  3. Generate (unique, not copied). 
    python scripts/generate_submission.py --template data/sample_submission.tif --features data/training_features.tif --mode dotted-ridge --dots 37654
# or for the continuous prior:
python scripts/generate_submission.py --template data/sample_submission.tif --features data/training_features.tif --mode structural-prior
    This writes docs/submissions/<name>.tif + .tif.json sidecar + .zip. Each name is unique (timestamped, mode-tagged) and the SHA-256 is recorded in the sidecar.
  4. Validate automatically (no human needed). 
    python scripts/validate_submission.py docs/submissions/<name>.tif --template data/sample_submission.tif
# with labels/features for holdout + leakage canary:
python scripts/validate_submission.py docs/submissions/<name>.tif --template data/sample_submission.tif --labels data/labels.tif --features data/training_features.tif
    Checks: driver GTiff, 1 band float32, CRS == template, shape == template, transform == template, every value in [0,1], 0 NaN/Inf inside footprint, footprint overlaps template. Writes <name>.tif.validate.json and prints JSON. Exit code 0 = format OK. Only when format_valid: true and the sidecar says illustrative_fallback: false is the file ready for the portal.
  5. Submit on DrivenData. On the New submission form, upload the .tif (or .zip), paste the unique submission name (e.g. gemsdoe80-dotted-ridge-v2-20261021T231505Z) and a short Note (≤140 chars, e.g. Dotted Walker-Lane ridges 37654 dots, 2% scatter, credit-dense thinning, strain+mag prior; label-free, unique. 137 chars). The portal will accept the file only if its values are in [0,1] and its grid matches exactly — the validator above checks this before you spend a weekly slot. Retain the organizer's receipt; that is the only ORGANIZER-CONFIRMED score.

What to submit as File to submit: a single-band GeoTIFF .tif or a .zip containing exactly one GeoTIFF. Both are offered here; either is accepted by DrivenData.

What to put in Note (optional): a ≤140-character comment to tell submissions apart later (shown on the leaderboard). Example for this file: Dotted Walker-Lane ridges 37654 dots, 2% scatter, credit-dense thinning, strain+mag prior; label-free, unique.

Requirements the validator enforces: CRS EPSG:32611 (UTM 11N), 100 m resolution, same bounds/shape/geotransform as sample_submission.tif, single band float32, values in [0,1], NaN/null outside footprint only. See official spec at Problem description and Submission guidance PDF.

Why the [0,1] error happened and how we fixed it — verified line by line

DrivenData rejects any value outside [0,1] and also rejects the float32 sentinel -3.4028234663852886e+38 (used as nodata in training_features.tif: 7,113,308 cells, 3,061 inside the footprint per GEMSDOE32). Two mechanisms produce the same message:

  • Sentinel leak: writing nodata -3.4e38 through unchanged.
  • NaN/sentinel outside footprint with nodata tag: a future validator change could treat the tag itself as out-of-range.

Fix applied here (verified by re-reading written bytes): every TIF offered is written all-finite with nodata=None, clipped to [0,1], with 0 NaN, 0 Inf, 0 sentinel. Re-read confirmation for the primary:

EPSG:32611  3000×4000  float32  nodata=None  min 0.02  max 1.0  0 NaN  0 Inf  0 sentinel  0 out-of-range  37654 dots ≥0.9

Validated with scripts/validate_submission.py (exit 0 when self-checked). Independent sidecars and SHA-256 are published alongside each TIF.

What we learned from the 0.2778 leader and how this file is different

The best GEMSDOE site reports h33-h33-2-b2-20261004T220000Z-e5eb6e7e-zeros: 0.2778 (37,654 dots, 0 within 200 m of the catalogue) and the public leaderboard high is cited as 0.3262 (#1 nchuzhoy) / 0.3195 (#2 DARD) — figures we flag as unverified until seen on a dated organizer receipt.

  • Mechanism: DTI is a credit budget (break-even per dot ≈0.052). Thinning a thick 121k solid to 37–44k dotted raises mean credit per dot; smoothing for the ~1.85 px scatter before greedy packing adds another +0.014 to +0.025 (GEMSDOE32 monte-carlo).
  • This file: implements dotted thinning itself — 37,654 high-confidence dots on Walker-Lane-parallel linear ridges (not the prior blob), with explicit relay-ramp halos and 2% scatter. It is rank-uncorrelated with any registry blob raster by construction; lane check vs registry >0.90 / 70% overlap is satisfied.
  • To beat 0.2778 for real: a detector with holdout AUC >0.681 plus scatter-aware packing is needed. This unique synthesis demonstrates the emission side; the detector side requires real training (labels + features) and a spatially-blocked holdout. No score claim is made here.

Parallel-run protocol (how we avoid wasting your weekly slot)

  • LANE: stay in the dotted-ridge lane; if rank-correlation >0.90 or >70% dots within 3 px of a registry raster, log duplicate and stop.
  • REUSE, DON'T REBUILD: shared tools live in scripts/ (cached feature stack, evaluate_holdout.py analogue in validate_submission.py, submission_writer.py analogue in generate_submission.py).
  • LABEL EVERY NUMBER: HOLDOUT-DTI (evaluator version + withheld positives + 95% CI) or ORGANIZER-CONFIRMED (copied from receipt). A projection is never a score.
  • LEAKAGE CANARY: AUC per feature on holdout; >0.90 = leakage until proven otherwise.
  • RUN CARD: one JSON per experiment at research/run-card.json. Negative results are deliverables.
  • BUDGET: 3 experiments / 2 hours max; do not spend a submission slot on an idea that hasn't beaten the holdout best.
