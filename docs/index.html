Executive summary: how a submission is made

The competition takes one single-band float32 GeoTIFF (or a .zip holding one) with values in [0, 1], in EPSG:32611 at 100 m, on the exact grid of the official sample_submission.tif, with null/NaN outside the bounds. Source: problem description, submission format. The cap is three submissions per week (rules §3.2).

  1. You place the data. On a logged-in machine, download the four files from the DrivenData data page into data/. Keep them out of git.
  2. Check placement: python scripts/prepare_data.py prints the official grid.
  3. Generate: python scripts/generate_submission.py --template data/sample_submission.tif --features data/training_features.tif --name <unique-name> --note "clustering with k=25". It writes an ungated candidate to artifacts/candidates/ (git-ignored) and refuses (exit 2 or 3) unless the grid matches the template exactly.
  4. Validate: python scripts/validate_submission.py artifacts/candidates/<name>.tif --template data/sample_submission.tif --labels data/labels.tif --features data/training_features.tif. It checks the format, the range, and the NaN rule, and reports an internal holdout DTI with a CI and the leakage canary.
  5. Submit only when validation passes, the holdout gate passes, and a person chooses the slot. Give the file a unique name and a note of 140 characters or fewer. Include the generative-AI disclosure the rules require. Keep the public name and note generic.

Why did 0.2778 score, and can we beat it?

  • The 0.2778 is owner-reported, not verified. The GEMSDOE32 repo lists that exact file as UNSCORED with no receipt, and gives it a catalogue-proxy DTI of 0.0067. The public leaderboard shows 0.2778 at rank #48 under the DrivenData user extradr19, with no file hash, so the two can't be linked. OWNER-REPORTED
  • What the file is: a binary dot raster, 37,654 dots, made by deleting dots within 2 px of the USGS catalogue from a 0.2708 base. Its "projected live 0.2747" is a projection, not a score.
  • Why deleting catalogue-flank dots can help under this metric (analysis): α = 0.2 and β = 0.8 make a wrong dot cheap and a dot within 3 px of a true fault valuable. The official page says test faults are not in the USGS catalogue, so catalogue-flank dots mostly add false-positive weight. This holds only if new faults don't cluster on the same flanks, and that can be tested only with labels.
  • Can we beat 0.2778? Not demonstrated. Nothing here has been measured on the competition data, and no claim is made. The route is on this page below.

Candidate hypotheses (not validated)

C1 · rank 1

Linear ridge continuity from magnetic edges

Layers: magnetic RTP/TMI and slopes. Long, connected linear magnetic contrasts that are absent from the catalogue. Mimic: dikes and contacts. Differs from H1 by testing linearity and continuity.

C2 · rank 2

Multi-physics coincidence gating

Layers: magnetic edge, gravity gradient, conductivity contrast, strain, seismicity. Min or product across independent contrasts instead of H1's mean. Mimic: lithologic contacts.

C3 · rank 3

Metric-aware emission

Scoring-side only: dot spacing matched to the 3 px kernel, and low-confidence mass removed. Must be measured against a density-matched control.

1 m lidar scarps

High value, but the DEM tiles need the DrivenData login or public USGS 3DEP access (not verified from here).
