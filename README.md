## 1. Executive summary — how to make a submission (once the data is in place)

The entry is **one single-band float32 GeoTIFF** (or a `.zip` holding one), with these properties
(official page, "Submission format"):

| Requirement | Value | Verified |
|---|---|---|
| CRS | EPSG:32611 (UTM 11N) | OFFICIAL-PAGE |
| Resolution | 100 m | OFFICIAL-PAGE |
| Bounds | same as the training data; outside the bounds, null/NaN | OFFICIAL-PAGE |
| Layers | one, `float32` | OFFICIAL-PAGE |
| Values | 0 to 1 inside the footprint (higher = more likely fault) | OFFICIAL-PAGE |
| Exact shape + geotransform | must equal `sample_submission.tif` | OFFICIAL-PAGE (the template itself is login-gated) |
| Weekly cap | 3 submissions per week | OFFICIAL-PAGE (rules §3.2) |

**Steps (only after you place the files):**

1. **You** log in to DrivenData and download `training_features.tif`, `labels.tif`, `sample_submission.tif`,
   `1m_DEM_links.csv` into `data/` (git-ignored; never commit them).
2. `python scripts/prepare_data.py` → confirms placement and prints the official grid.
3. `python scripts/generate_submission.py --template data/sample_submission.tif --features data/training_features.tif`
   → writes to `docs/submissions/` **only if** the features grid equals the template grid; otherwise it refuses (exit 3)
   or, with missing inputs, writes nothing (exit 2).
4. `python scripts/validate_submission.py docs/submissions/<name>.tif --template data/sample_submission.tif --labels data/labels.tif --features data/training_features.tif`
   → format checks, internal holdout DTI with a CI, and the leakage canary.
5. Submit only when the validator passes **and** a human decides the slot. `download_ready` stays `false` until an
   organizer receipt is recorded. Include the generative-AI disclosure (rules §3.2) and keep the public name and
   comment generic (rules A.4).

- **What the file is, per its own audit:** a 0.2708 base in which every dot within 2 px of the USGS catalogue was
  removed, leaving 37,654 dots, a binary (0/1) raster. Its own "projected live 0.2747" is a **projection**, not a score.
- **Why this direction helps under the official metric (analysis, not a measurement):** with α = 0.2 < β = 0.8,
  a dot is cheap if it is wrong (0.2 × its FP weight) and valuable if it sits within 3 px of a true fault. Test faults
  are, by the official page, faults **not** in the USGS database. Dots on the catalogue flanks therefore carry FP
  mass wherever the new faults do not run. Removing them can only help the FP term, provided new faults do not
  cluster on the same flanks. That premise is testable only with labels.
- **Why it could be luck:** the public leaderboard is a public subset (the private set decides the prize), and the
  top public score is 0.4413, so the metric is far from saturated and a single rank-48 number says little.
- **Can we beat 0.2778?** **Not demonstrated, and no claim is made.** Nothing in this repo has been measured on
  the competition data. Any statement that a candidate beats 0.2778 would be fabricated. The route is in §6.

## 6. Method (the parallel-run protocol) and the fixed tools

The protocol and its six rules are in the session prompt (Appendix). How this repo applies them:

1. **Lane.** Duplicate check: rank correlation > 0.90 with any registry raster, or > 70 % of dots within 3 px of
   one registry raster's dots. Not runnable yet: no registry rasters and no candidate.
2. **Reuse.** One validator, one generator, one template. Fixed this session: the DTI (wrong FN_w; centre pixel
   excluded), the CI (was invalid), the canary (had no negatives), and the generator (invented zones; no-op grid check;
   wrong output path); GeoTIFF tiling that failed on any grid whose width is not a multiple of 16; segment connectivity (4→8) and the buffer shape (square→disk). Details: IR-02, IR-03.
3. **Labels.** Every number carries HOLDOUT-DTI (evaluator version, withheld positives, CI) or ORGANIZER-CONFIRMED
   (copied from a receipt). **No such number exists yet.**
4. **Leakage canary.** Per-band AUC on held-out positives versus in-domain negatives; flags AUC > 0.90. Tested on
   synthetic data only.
5. **Run card.** `research/run-card.json`: E1 tooling done; E2–E4 not run; verdict negative.
6. **Budget.** Three experiments or two hours. Not spent on competition data yet.

**Holdout protocol (internal, not the organizer's):** a seeded random one-third of whole fault segments (8-connected components) are withheld.
Pixels within 300 m of a visible fault are excluded from scoring, and pixels outside the template footprint are
excluded. The CI is a cluster bootstrap over segments. **Limits:** the split is random rather than spatially
blocked, and features are not re-derived from the visible faults only. Both are listed as TODO in §8.

## 8. Limitations and next steps (ordered)

1. **Data placement (blocker).** The user places four files in `data/`. The sandbox cannot do this (§3).
2. **Verify the grid.** Once `sample_submission.tif` is local, record its shape, geotransform and SHA-256 in the run card.
   Compare against the third-party 3730×3292 claim. Do not rely on the third-party claim.
3. **Verify band names.** Print every band's description (`prepare_data.py`). Check that the generator's keyword
   matching finds each intended term. Record the term list in the sidecar (IR-08).
4. **Run E2 and E3 on the holdout.** The first real numbers, labelled HOLDOUT-DTI with count and CI.
5. **Make the holdout spatially blocked** (block-level segment withholding with a buffer) and derive all
   catalogue-based features from visible faults only. Current holdout is random by segment (TODO).
6. **Organizer questions:** deadline clock (IR-11), whether third-party data mirrors are acceptable (IR-01),
   and the generative-AI disclosure wording (IR-12).
7. **Licensing.** Confirm the licence of every external layer before use (rules A.5 and the homepage "external data" note).
8. **Lidar (C4).** Decide whether to obtain the 1 m DEM tiles. Obtainability from official USGS sources is not yet verified.
9. **What the validator cannot prove.** It scores a finished raster. It cannot tell whether a model was trained on held-out labels, or whether features were derived from withheld faults. Those are properties of the pipeline, so every run must record its own training split, and any leakage check must sit upstream of the validator.
10. **Segment definition.** Segments are 8-connected components of the label raster. A rasterisation that splits a fault into disconnected pieces can still leak across the split. Check the segment count on the real labels.
